# Deployer audit - 2026-09-28

## Executive summary

**Overall health: good code, risky edges.** The core is careful work. Refresh tokens rotate with reuse detection, OAuth uses PKCE plus a browser-bound nonce, identifiers are regex-checked before DDL, secrets stay out of argv, backups use chunked AES-GCM, and the installer verifies every download. The test suites pass: the API has about 580 tests with 22 env-gated skips, the dashboard has 207, and ruff is clean. Most problems fall into three groups:

1. **Trust boundaries that are wider than the docs say.** The mongosh console runs in the API container. `anon` keys can read everything. The "read-only" check is a text filter. App containers share the API's network.
2. **Failure and recovery paths nobody exercises.** Timeouts are not enforced, jobs get stuck "running", retries fail, and integration tests never run in CI.
3. **Places where the platform assumes the user knows networking.** Links are built from localhost, the dashboard gives raw `docker compose` commands, and error text is jargon.

This report keeps 198 findings (1 critical, 17 high, 82 medium, 98 low) after merging cross-section duplicates. Two findings were refuted. Cloud hosting was not reviewed.

### Top 5 risks

1. **A-001 (critical):** mongosh gives project developers and `service` keys full Node inside the API container. From there they can read MASTER_KEY, JWT_SECRET and the root DB passwords from `/proc/1/environ`, which turns a project role into control of the whole machine.
2. **A-004 / A-005 / A-006 / A-018:** the `anon` key is advertised as safe for browsers. In fact it reads every table, and its "read-only" SQL and Mongo checks miss `setval`, `pg_terminate_backend`, `dropAllUsers` and `changeUserPassword`. The API also has no CORS support, so the browser use case cannot work anyway.
3. **A-002:** unauthenticated logins with random emails each run a 64 MiB argon2 hash with no cap on concurrency. About 12 parallel requests OOM the 768 MB API container.
4. **A-008 / A-011:** moving a database loses writes that live apps keep sending to the old copy. One large transaction permanently stops a co-host copy's sync.
5. **A-012:** `DockerCli._run` never enforces its timeout on a silent process. One hung `git clone`, or an `npm start` used as the build command, ties up one of two worker runners forever, and scheduled backups stall behind it.

### Top 5 usability problems for non-experts

1. **A-003:** there is no way to recover a forgotten password, even for the owner. The only fix is editing MariaDB by hand or reinstalling.
2. **A-017:** on a PC without AVX (the target hardware), the very first "New project" fails, because the MongoDB box is ticked by default.
3. **A-016:** everyone who signs up through an invite link then sees "This invite isn't valid", even though they joined.
4. **A-020 / A-055 / A-014:** invite links, app links and GitHub webhooks are built from `http://localhost` or a public host that does not serve them. Nothing warns about it, and nothing re-syncs them after remote access is set up.
5. **A-015 / A-082:** Stop does not stop Deployer (the autostart loop restarts it after 15 s). When remote access breaks, the dashboard tells users to run raw `docker compose` commands that do not exist on the default WSL install.

## Usability for non-experts

This follows the path a person with no networking or database background takes, from download to daily use.

### Journey 1: Install on an old PC
**What works:** The system check (Core.cs:309-455) turns every problem into a plain instruction, for example how to enable virtualization in the BIOS, with a help link. It picks a free port for you. It pre-selects the free WSL runtime. Secrets are generated locally.

**Friction:**
- The Options page shows a bare "Port" box (A-198). Suggested wording: *"Web address number (port) - leave as is unless setup says it's taken"*, placed under a collapsed "Advanced options".
- A full C: drive gives a dead end. The check says "choose a different drive on the Options page" but blocks the Next button (A-154).
- A 4 GB PC is told Deployer "works", but WSL gives it about 2 GB (A-070). Suggested wording: *"About 2 GB is available to Deployer; expect 1-2 small apps."*
- ARM64 users wait through a local build that always fails (A-066). Refuse ARM64 up front.
- If a standard user types an admin's password at the UAC prompt, Deployer is installed for the admin account (A-079).
- If the install fails partway, running setup again opens Deployer Control on a half-installed stack (A-073). The uninstaller then says "all data removed" when it removed almost nothing (A-078).
- Error hints tell the user to run `deployer logs api` before `deployer` is on the PATH (A-147).

### Journey 2: First run and owner account
**Friction:**
- The password box says "at least 8 characters", but the server needs 10 (A-080).
- The "Public URL" step asks about Tailscale and OAuth callbacks on screen two (A-083). Suggested wording: *"Leave this as it is for now. When you want people on other devices or the internet to reach Deployer, go to Settings > Domains & remote access; it sets this for you."*
- Forms say "Invalid request" without naming the field (A-022).
- If the owner forgets the password, they are locked out for good (A-003). Add a *"Forgot your password? On the Deployer PC open Deployer Control > Reset password"* link.

### Journey 3: Create a project, a table and some rows
**Friction:**
- On a PC without AVX, the first "Create" fails with a CPU-instruction error (A-017). Suggested hint: *"This PC's processor can't run MongoDB; you can connect a free MongoDB Atlas database later."*
- Create table is raw SQL: BIGINT UNSIGNED, Nullable, "On delete: cascade", and "(convention S1)" (A-098, A-176). Offer friendly types first: Text, Whole number, Yes/No, Date, Link to another table. Rename "Nullable" to "Can be empty".
- Typing "true" into a yes/no column gives `(1366, "Incorrect integer value...")` (A-097).
- The row editor loses focus at the 81st character (A-086).
- The connection details dialog says "Docker network" twice. It also says the URI works from every app, which is false (A-026).

## Refuted findings

Do not re-report these without new evidence.

- **"Up to 4 concurrent mongosh processes share the API's 768 MB limit, so the API is OOM-killed"** (query_console.py:52, 623-644). Refuted. The finding was an estimate, not a measurement. Four Node processes plus uvicorn come close to 768 MB, not clearly over it, and reaching that needs four concurrent admin shells. On a cgroup OOM the kernel kills the highest oom_score process, normally a mongosh child rather than uvicorn (PID 1). So one query fails with the existing "The shell exited with status N" message, and the container does not restart. A `--max-old-space-size=128` cap would be cheap hardening, not a bug fix.
- **"Any non-OK refresh response (e.g. 502 during an API restart) signs the user out"** (dashboard/src/api/client.ts:155-159). Refuted. `refresh()` runs only after a 401, and a restarting API returns 502, not 401, so the in-memory token survives the restart. At boot the user is already null, so `emit(null)` changes nothing, and the proposed fix leads to the same /login. Only a millisecond race remains, which is polish at most.
- **Partial correction (merged finding A-075):** the exe finding said the wizard "silently turns on WSL mirrored networking". install.ps1:850-851 does set `$useMirrored = $true` when NonInteractive, but Enable-DeployerLanAccess (common.ps1:1121-1127) forces it back to `$false` before any `.wslconfig` edit, so nothing is changed. That dead path is A-065.
